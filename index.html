TUTORIAL TÉCNICO

Como o EmotiAI Vision enxerga participação em sala de aula

Este guia explica, módulo por módulo, o código real do projeto: uma pipeline local de visão computacional que estima postura corporal e participação observável a partir da câmera — sem reconhecer rostos, sem identificar pessoas e sem gravar imagem ou vídeo.

SEM RECONHECIMENTO FACIAL O sistema não processa identidade — apenas pontos anatômicos (ombros, cotovelos, punhos) de silhuetas.
SEM ARMAZENAMENTO Nenhum frame ou vídeo é salvo em disco. Só métricas agregadas e anônimas chegam ao console.
IDENTIDADE TEMPORÁRIA IDs como track_1 existem apenas durante a sessão em execução e são descartados ao final.

Arquitetura da pipeline

Cada frame da câmera passa por seis estágios até virar uma métrica de participação. Nenhum estágio conhece a implementação do anterior — eles se comunicam por objetos simples (dataclasses), o que torna cada peça testável isoladamente.

PASSO 1

Captura de vídeo

A câmera é a única fonte de dados do sistema. CameraCapture encapsula o cv2.VideoCapture e devolve frames já rotacionados, sem nunca gravá-los em disco.

camera/capture.pyOpenCV
class CameraCapture:
    def open(self) -> None:
        self._camera = cv2.VideoCapture(source)
        self._camera.set(cv2.CAP_PROP_FRAME_WIDTH, self.config.width)
        self._camera.set(cv2.CAP_PROP_FRAME_HEIGHT, self.config.height)
        self._camera.set(cv2.CAP_PROP_FPS, self.config.fps)

    def read(self) -> np.ndarray:
        success, frame = self._camera.read()
        if not success or frame is None:
            raise CameraError("Falha de leitura ou câmera desconectada")
        return self._rotate(frame)
Por que assim: a classe usa o protocolo __enter__/__exit__ (context manager), então with CameraCapture(...) as camera: garante que release() seja chamado mesmo se o programa quebrar no meio — a câmera nunca fica "presa" por um processo travado.

Configuração

Resolução, rotação e fonte de vídeo vêm de camera/config.py, um dataclass simples que main.py preenche a partir de Settings. Isso mantém a captura agnóstica: ela não sabe nada sobre postura, tracking ou métricas — só entrega frames.

PASSO 2

Detecção de pose com MediaPipe

Cada frame passa pelo modelo pose_landmarker_lite.task do MediaPipe, que devolve até 33 pontos anatômicos (landmarks) por pessoa — sem qualquer dado de identidade.

detection/pose_detector.pyMediaPipe Tasks
def detect(self, frame: np.ndarray, timestamp_ms: int) -> list[DetectedPose]:
    rgb = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)
    image = self._mp.Image(image_format=self._mp.ImageFormat.SRGB, data=rgb)
    result = self._landmarker.detect_for_video(image, timestamp_ms)

    poses: list[DetectedPose] = []
    for landmarks in result.pose_landmarks:
        pose = PoseLandmarks(list(landmarks))
        confidence = pose.confidence("left_shoulder", "right_shoulder")
        poses.append(DetectedPose(landmarks=pose, confidence=confidence))
    return poses

O modo RunningMode.VIDEO foi escolhido em vez do modo de imagem única porque ele usa o timestamp de cada frame para manter coerência temporal entre detecções — importante, já que o sistema roda em fluxo contínuo, não em fotos isoladas.

Um adaptador em vez de números mágicos

pose_landmarks.py nomeia os 33 índices do MediaPipe (left_shoulder, right_wrist, left_hip...) e obriga o resto do projeto a usar esses nomes em vez de landmarks[15]. A classe também calcula confidence() como o mínimo entre visibility e presence do MediaPipe — uma decisão conservadora: só considera um ponto confiável quando as duas métricas concordam.

detection/pose_landmarks.py
LANDMARK_INDEX = {
    "left_shoulder": 11, "right_shoulder": 12,
    "left_elbow": 13,   "right_elbow": 14,
    "left_wrist": 15,   "right_wrist": 16,
    # ... até 33 pontos (rosto, tronco, pernas)
}
PASSO 3

Rastreamento por proximidade

O MediaPipe não sabe quem é quem entre um frame e outro — só devolve poses soltas. O PoseTracker resolve isso comparando a distância entre o centro dos ombros de cada pose e os tracks já existentes.

tracking/tracker.py
for distance, track_id, pose_index in sorted(candidates):
    if distance > self._max_distance or track_id in matched_tracks:
        continue
    track.update(pose.landmarks.center(), pose.landmarks, pose.confidence, timestamp_ms)
    # pose mais próxima "vence" e atualiza o track existente
Por que assim: ordenar todos os pares (distância, track, pose) e consumi-los do mais próximo para o mais distante é um casamento guloso (greedy matching) — simples de entender e rápido o bastante para rodar em tempo real, já que o número de pessoas em uma sala é pequeno.

Poses que não casam com nenhum track viram uma pessoa nova (track_N). Tracks que não recebem atualização por tracker_max_missed_frames frames seguidos são considerados perdidos e removidos — isso absorve oclusões curtas (alguém passando na frente) sem criar um ID novo para a mesma pessoa.

PASSO 4

Análise de postura: braço levantado

A "IA" de decisão aqui não é um modelo treinado — é uma regra geométrica interpretável sobre os landmarks, decidida por ArmRaisedRule e confirmada ao longo do tempo por PostureAnalyzer.

A regra geométrica

analysis/arm_detection.py
def _is_raised(self, pose, side: str) -> bool:
    wrist_above_shoulder = float(wrist.y) < float(shoulder.y) - self._wrist_margin
    elbow_above_hip = float(elbow.y) < float(hip.y)
    return wrist_above_shoulder and elbow_above_hip

Como no sistema de coordenadas de imagem o eixo Y cresce para baixo, "punho acima do ombro" vira wrist.y < shoulder.y. A margem de 0.035 evita que pequenos tremores classifiquem um braço parado como levantado. Quando o quadril não está visível (pessoa sentada, fora de quadro), a regra cai para uma versão mais simples e ainda assim conservadora: só olha punho e ombro.

Confirmação temporal

PostureAnalyzer não confia em um único frame — ele exige required_consecutive_frames (padrão: 5) frames seguidos no mesmo estado antes de confirmar uma transição, e trata um lado sem confiança como "estado desconhecido" em vez de "braço abaixado", para não gerar eventos falsos por oclusão momentânea.

analysis/posture_detection.py
if state.candidate_state == candidate:
    state.candidate_frames += 1
else:
    state.candidate_state = candidate
    state.candidate_frames = 1

if state.candidate_frames < self._required_frames:
    return result, []  # ainda não é estável o suficiente
PASSO 5

Eventos

Toda transição de estado relevante — pessoa detectada, pessoa perdida, braço subiu ou desceu — vira um VisionEvent: um registro imutável com tipo, id do track, confiança e timestamp.

events/event.py
class EventType(StrEnum):
    PERSON_DETECTED = "PERSON_DETECTED"
    PERSON_LOST = "PERSON_LOST"
    LEFT_ARM_RAISED = "LEFT_ARM_RAISED"
    RIGHT_ARM_RAISED = "RIGHT_ARM_RAISED"
    BOTH_ARMS_RAISED = "BOTH_ARMS_RAISED"

EventManager apenas cria o evento e escreve uma linha de log — ele não guarda histórico em memória além do lote atual. Isso é proposital: eventos são um fluxo passageiro, quem precisa de memória de mais longo prazo é o próximo estágio, o agregador.

PASSO 6

Métricas agregadas e participação

A cada janela de aggregation_window_seconds (padrão: 10s), o MetricsAggregator resume tudo o que aconteceu em um único JSON — a única saída de dados do sistema além da janela de debug.

analysis/aggregator.py
report = {
    "people_average": round(average, 2),
    "people_max": max(self._people_samples, default=0),
    "participating_people": len(self._participants),
    "arm_raise_events": self._arm_raise_events,
    "participation_ratio": round(participation_ratio(...), 3),
}

A taxa de participação em si é uma função quase trivial — de propósito:

analysis/participation.py
def participation_ratio(unique_participants: int, average_people: float) -> float:
    """Participação observável; não é uma medida de satisfação ou emoção."""
    return unique_participants / average_people if average_people > 0 else 0.0
Por que assim: o comentário no próprio código já é a justificativa de projeto mais importante do sistema — a métrica descreve quantas pessoas levantaram o braço ao menos uma vez dentro da janela, não estado emocional, engajamento subjetivo ou atenção. É um limite deliberado para não superinterpretar um sinal puramente geométrico.

PASSO 8

O loop principal

main.py não implementa nenhuma regra de visão — ele só orquestra a ordem: câmera → detecção → tracking → análise → eventos → agregação → (opcional) renderização. Também controla a taxa de processamento, independente da taxa de captura da câmera.

main.py
if now - last_processed_at >= period:  # limita a target_processing_fps
    poses = detector.detect(frame, timestamp_ms)
    tracking = tracker.update(poses, timestamp_ms)

    for track in tracking.tracks:
        detected, transitions = analyzer.analyze(track)
        emitted.extend(events.create(ev, track.track_id, detected.confidence, timestamp_ms)
                       for ev in transitions)

    latest_metrics = aggregator.update_realtime(latest_tracks)
    aggregator.ingest(timestamp_ms, latest_metrics.people_detected, emitted)
Por que assim: separar period (taxa de processamento, ex. 10 FPS) da taxa real da câmera (ex. 30 FPS) evita gastar inferência do MediaPipe em frames redundantes — a câmera continua fluindo, mas só 1 em cada 3 frames é de fato analisado.

Como executar
